2026-11-03。実装と検証を同じワークスペースで行いました。実機はTinyGo Conference 2026 badge(ESP32-S3)とGopher Board(RP2040-Zero)で確認しました。ESP32無印は実機が未接続のため未確認です。

- Go 1.27.1、Linux amd64
- TinyGo 0.44.0、LLVM 22.1.4（このマシンのインストール）
- drivers v0.37.0、tinyfont v0.7.0
- 互換ビルド: Ebitengine v2.10.5、GOOS=js、GOARCH=wasm

書き込み制限のある環境では `GOCACHE=/tmp/ikaten-go-cache`、`XDG_CACHE_HOME=/tmp/ikaten-cache` を指定しました。TinyGoのキャッシュはXDG_CACHE_HOMEの下に置きます。この環境の.gitは通常のリポジトリとして読めないため、ビルドには `GOFLAGS=-buildvcs=false` を使用しました。

## メモリと割り当て

`tinygo build -size short` のbounceサンプルの結果です。RAM欄は **data + bssのみ**で、起動後のヒープや実行時スタックの使用量を含みません。

| ターゲット | code | data | bss | flash合計 | 静的RAM合計 |
| --- | ---: | ---: | ---: | ---: | ---: |
| badge | 63,632 | 3,208 | 21,312 | 66,840 | 24,520 |
| esp32s3 | 60,624 | 3,168 | 21,240 | 63,792 | 24,408 |
| esp32 | 61,576 | 3,216 | 5,368 | 64,792 | 8,584 |
| pico | 56,328 | 3,304 | 6,364 | 59,632 | 9,668 |
| gopher-badge | 56,296 | 3,376 | 6,364 | 59,672 | 9,740 |

フラッシュ画像のサンプル（badge）の文字列埋め込み版はdata=3,200B、bss=21,304B。変更前の可変 `[]byte` 埋め込み版ではdata=3,752B、bss=21,856Bで、ファイル本体相当の静的RAM増加を確認しました。画像は `NewImageFromString` によりコピーせず参照します。

GoのAllocsPerRunで、Clear/Fill/DrawImage（平行移動と回転）/行読み出し、Presentの変更なしフレーム、文字、図形、キー列挙の継続処理が **0 allocs** になることを確認しました。

`tinygo build -print-allocs=.` をbounceとsnakeに実行しました。エンジンとドライバで報告された箇所は、画像、ボタン状態、液晶の初期化、初回または解像度変更時のPresentバッファの確保だけで、Update、Draw、文字描画、変更行処理には報告されませんでした。snakeでは毎フレームの `fmt.Sprintf` と `append` がゲーム側の確保として報告されます(元のソースのままです)。SubImageと動的Layoutの再確保は許容しています。

ホストの16×16不透明スプライト描画ベンチマークは約208ns/op、0B/op、0allocs/opでした（Core i5-1145G7）。**この値は実機の性能予測には使用しません。**

## バッジでの実測

環境はTinyGo Conference 2026 badge(ESP32-S3、240MHz)、既定の `-opt=z` です。生ログは [measurements/2026-11-03-badge.txt](measurements/2026-11-03-badge.txt) にあります。

### SPI全画面転送(240x240、1フレームあたり)

| 要求周波数 | 1行ずつ | 4行ずつ | 計算上の下限 |
| --- | ---: | ---: | ---: |
| 20MHz | 56.4ms | 52.0ms | 46.1ms |
| 40MHz | 32.5ms | 28.6ms | 23.0ms |
| 80MHz | 20.7ms | 17.0ms | 11.5ms |

1行転送と4行転送の差から、転送の窓設定は1回あたり約21µsです。全行変更時に連続行をまとめると、80MHzで約3.7ms短縮できます。

**決定:** バッジのSPI既定値は80MHzにしました。目視で表示の乱れがなく、40MHzより全画面転送が約12ms短いためです。汎用の `esp32s3` ターゲットは配線と液晶が不明なので40MHzのままです。連続行の統合は実装しますが、効果がより大きい `Present` の高速化と合わせて行います。

### スプライト描画(16x16、1枚あたり)

| 画像 | 変更前 | 変更後 |
| --- | ---: | ---: |
| RAM、不透明 | 55.2µs | 56.0µs |
| RAM、マスク付き | 129.2µs | 54.6µs |
| フラッシュ、不透明 | 145.2µs | 46.7µs |
| フラッシュ、マスク付き | 132.8µs | 63.9µs |

変更後はフラッシュとRAMの差が小さく、頻用画像をRAMへコピーする必要はありません。

**判断(タスク3):** マスク付き30枚のシーンは約60msで33.3msに収まらなかったため、高速経路を実装しました。bounceをマスク付きにしたときの `Draw` は8.8msから約6.95msに短縮しました。ただし、FPSはほぼ変わりません。支配的なのは `Present` です。

### benchmark(240x240、スプライト30枚)

| 構成 | FPS | TPS | Draw | Present |
| --- | ---: | ---: | ---: | ---: |
| 40MHz、`-opt=z` | 15〜16 | 46〜48 | 6.4ms | 61.7〜61.9ms |
| 80MHz、`-opt=z`、高速経路の実装前 | 16〜18 | 50〜56 | 6.4ms | 51.0〜51.4ms |
| 80MHz、`-opt=z`、高速経路の実装後 | 16〜18 | 50〜56 | 6.5ms | 51.2〜51.5ms |
| 80MHz、`-opt=z`、マスク付き、実装後 | 16〜18 | 50〜56 | 7.0ms | 51.1〜51.5ms |
| 40MHz、`-opt=2`、実装前 | 16〜17 | 49〜51 | 6.4ms | 53.5〜54.5ms |
| 80MHz、`-opt=2`、実装前 | 19〜21 | 57〜60 | 6.4ms | 43.2〜44.0ms |

この時点では性能目標の30 FPS / 60 TPSは未達でした。1フレームが約58msかかり、1回の描画あたりの `Update` が上限の3回に達するため、TPSも60を下回りました。画面が変わらないフレームでも `Present` は22.9msかかっていました(`-opt=z`、行の読み出しとハッシュの計算)。

### `Present` の高速化

等倍でフレームバッファをコピーせず転送し、連続する変更行を1回の転送にまとめ、ハッシュを16bit単位にして、行の展開を拡大時だけにしました。同じbenchmarkの結果です。

| 構成 | 10秒あたりのフレーム数 | TPS | Draw | Present |
| --- | ---: | ---: | ---: | ---: |
| 80MHz、`-opt=z` | 425〜433 | 60 | 6.5ms | 16.6〜17.0ms |
| 80MHz、`-opt=z`、マスク付き | 419〜427 | 59 | 6.8ms | 16.6〜17.0ms |
| 80MHz、`-opt=2` | 418〜426 | 59〜60 | 6.6ms | 16.9〜17.3ms |
| 40MHz、`-opt=z` | 294〜301 | 60 | 6.5ms | 26.8〜27.5ms |

変更のないフレームの `Present` は22.9msから2.7msになりました。

**性能目標の30 FPS / 60 TPSをバッジで達成しました**(約43 FPS)。

**決定:** `-opt=z` のままにします。`-opt=2` に速度の利点がなくなり、コードだけが約74KBから約124KBに増えるためです。

`Present` はメモリ上のピクセルをそのまま送ります。可変画像の透明ピクセルは常に0で、黒への平坦化と同じ結果になるためです。この前提は `TestRGB565RowsMatchFlattenedRows` で確認しています。ハッシュの衝突で変更を見逃す可能性は、以前と同様に残ります。

高速化の後も、テスト、`make smoketest`(29ビルド)、`make compat`、`tinygo test`、`-print-allocs` の結果は変わらず成功です。`Present` のヒープ確保は初回と解像度変更時だけです。snakeのWASMの開始画面は変更前とピクセル単位で一致しました。

### 30分連続実行

`Present` の高速化後の最終コード、80MHz、bounce(スプライト30枚)で実行しました。

| 項目 | 結果 |
| --- | --- |
| 動作 | 30分後に `Termination` で正常終了。途中の停止なし |
| 描画フレーム数 | ログの179区間の合計で77,193 |
| `HeapAlloc` | 全区間で134,368B(増加なし) |
| FPS / TPS | 40〜51 / 58〜61(平均 約42.7 / 約59.4) |
| `Draw` / `Present` | 約6.5ms / 16.2〜17.0ms |

高速化の前にも同じ30分の実行を行い、停止せず、`HeapAlloc` も同じ値でした(16〜19 FPS)。

ログ末尾の `abort called` は、TinyGoのESP32-S3で `main` が終了したときの通常の出力です(`exit` が `abort` を呼びます)。高速化前のログでは、シリアルの取りこぼしで1行の先頭が欠けています。

### 30分連続実行

bounce(スプライト15枚、120x120を2倍)で、計測値をシリアルではなく画面下に毎秒表示する版を使いました。シリアル出力の停止を避けるためです。2026-11-03 12:54に開始しました。

| 項目 | 結果 |
| --- | --- |
| 動作 | 30分後の `DONE 30min` まで停止なし(依頼者が確認) |
| 終了時の `HeapAlloc` | 228,664B |
| 終了時のGC回数 | 189 |

この版は、表示する文字列を毎フレーム `string([]byte)` で作るため、割り当てが発生します。bounce自体は割り当てがなく、シリアル計測では `HeapAlloc` が42,464Bのまま一定でした。TinyGoの `HeapAlloc` は回収前のごみを含むため(flappyのログでGCの前後に増減しています)、終了時の1回の値からは増加の有無を判断できません。189回のGCを経ても停止しなかったため、ヒープは回収されていると判断しました。

画面のfps=60は、30分経過後にシミュレーションを止め、文字だけが変わる状態での値です。実行中のFPSは上の表の値(約31.7)です。

## dungeon(オリジナルの一人称シューティング)

`games/dungeon` は、レイキャスティング方式の一人称シューティングを新規に書いたものです。マップ、敵(スライム)、武器、壁の模様はすべてコードで生成した独自のもので、既存のゲームの素材は使っていません。Ebitengine のAPIだけで書いているため、`make compat` でimportパスを書き換えるだけで本物のEbitengineでもビルドできます。

描画は、壁の縦1列ずつを1ピクセル幅の `SubImage` として拡大して描きます(120列)。距離による暗さは `ColorScale`、敵は奥から順に描き、壁より奥の列は飛ばします。

| 確認 | 結果 |
| --- | --- |
| WASM(ヘッドレスChromium、自動操作) | 壁、床、天井、武器、照準、マズルフラッシュ、HUDの描画を確認 |
| ホストのテスト(作業ツリー外のコピー) | スライムの表示と遠近、命中、被弾時の点滅、壁の向こうの敵に当たらないことを確認 |
| `make smoketest` | 8サンプル×6ボードと7サンプル×WASMの55ビルドすべて成功 |
| `make compat` | 成功 |

### Gopher Boardでの実測

120x120を2倍表示し、自動操作の計測版で測りました。シリアル出力が止まる問題(「RP2040のシリアル出力」参照)のため、10秒ごとの値を画面上部に表示し、依頼者が撮った写真から読み取りました。区間ごとの時間は、作業ツリー外のコピーで `Draw` に計測を加えた版のものです。

| 版 | 10秒あたりのフレーム数 | `Draw` | `Present` | 主な変更 |
| --- | ---: | ---: | ---: | --- |
| 最初 | 35 | 271.6ms | 20.1ms | — |
| 1 | 117 | 63.1ms | 22.0ms | 汎用経路の行の開始位置を固定小数点で足す |
| 2 | 161 | 41.1ms | 20.4ms | 回転のない拡大縮小を専用の経路にし、準備をfloat32にする。不透明な整数倍拡大を区間で書く |
| 3 | 205 | 28.7ms | 19.5ms | 同じソース行を使う行をまとめ、色を1回だけ計算して縦に書く。NaN判定と単位の `ColorScale` を浮動小数点なしにする |
| 4(最終) | 212 | 27.8ms | 18.9ms | `ColorScale` の変換をビット演算にする。区間の書き込みを直接行う |

最終版は約21 FPS、59〜60 TPSです。最終版の1フレームの内訳は、壁23.4ms(うち光線の計算5.2ms)、天井と床1.2ms、スライム0.3ms、武器とHUD0.8msです。計測値の文字表示に約0.9msかかっていますが、通常版にはありません。

RP2040(Cortex-M0+)には浮動小数点演算器がありません。最初の版では、1ピクセル幅の列を描くたびに汎用経路が行ごとにfloat64を計算しており、これが大部分でした。ソフトウェアのfloat32は1演算あたり約100サイクルと見積もられ(光線の計算から逆算)、最終版でも壁1列の `DrawImage` に約150µsかかります。その約3分の2は呼び出しごとの準備です。`Present` は画面全体が毎フレーム変わるため、2倍表示の転送に約19msかかります。30 FPSには `Draw` を約13msにする必要があり、DMA転送や第2コアの検討対象です。

計測中に `HeapAlloc` が増え続けていました。HUDの文字列を毎フレーム `string([]byte)` で作っていたためです。この変換は `-print-allocs` に表示されません。値が変わったときだけ作るように直したあとは、`gc=0` のまま増えなくなりました。

## all(全ゲームのランチャー)

`games/all` は、これまでのゲーム8本をメニューから選んで遊べるランチャーです。上下で選んでA(Z)で開始し、ゲーム中にAとB(ZとX)を1秒押し続けるとメニューに戻ります。押している間は画面上端にバーが伸びます。各ゲームのLayout(120x120または240x240)はそのまま使い、エンジンが画面を確保し直します。Ebitengine のAPIだけで書いているため、`make compat` で本物のEbitengineでもビルドできます。

`TestEveryGameStartsAndReturns` は、`RunGame` を通して8本を順にメニューから開き、少し遊んでからAとBを押し続けてメニューへ戻ることを確認します。blocksは最初の `Update` で場面を作るため、ゲームを選んだ直後に `Draw` が先に呼ばれるとpanicしました。Ebitengineと同じく、ランチャーはゲームが一度 `Update` するまで描画しないようにしました。

### バッジでのメモリ

作業ツリー外のコピーで、各ゲームを10秒ずつ順に開き、`runtime.GC` の後の `HeapAlloc` を表示しました。生ログは [measurements/2026-11-04-badge.txt](measurements/2026-11-04-badge.txt) の末尾にあります。

| 版 | 結果 |
| --- | --- |
| 最初 | flappy(240x240)からメニューに戻ると222KBに増え、blocks(240x240)を開いたところでメモリ不足で停止 |
| 画面のメモリを使い回す | 2周して停止なし。uboatで最大約307KB |
| uboatの大きな画像をフラッシュへ | 2周して停止なし。最大約203KB、flappyの後は194〜203KBで一定 |

1つ目は、Layoutが変わるたびに画面を新しく確保していたためです。古い画面はPCのGoでは回収されましたが、TinyGoの保守的なGCではスタックに残った古い値から参照されたままになりました。そこで `RunGame` の画面の確保し直しを、今の画面のメモリに収まる場合は使い回すように変えました(`resizeScreen`、`TestResizeScreenReusesMemory`)。画面のメモリは遊んだ中で最大のゲームの分(240x240で約122KB)を保持します。

`games/tank` は新規に書いた戦車戦です。砲手の照準器から見た3Dの戦場で、畑と村に散らばる敵戦車を撃破します。戦車、家、木、地面はすべて `assets/gen.go` がコードで描いた独自のもので、既存のゲームの素材や名前は使っていません。Ebitengine のAPIだけで書いているため、`make compat` で本物のEbitengineでもビルドできます。

- 操作: ジョイスティックの左右で砲塔を回し、上下で砲の仰角を変えます(押し続けると速くなります)。A(Z)で発射、Bを押しながらジョイスティックで車体を操縦(上下で後退、停止、半速、全速の4段階、左右で旋回)、Bを短く押すと照準器の8倍と広角を切り替えます。バッジの3つ目のボタン(Enter)でも切り替わります
- 車体と砲塔: 砲塔は車体と別に回り、車体が旋回しても砲塔は同じ方位を向き続けます(スタビライザー)
- 弾の落下: 弾は1ティックに10m進み、重力で落ちます。照準器の中心の下に200mごとの距離目盛り(2、4、6、8、10)があり、目標の距離の目盛りの間に目標を置くと当たります。目盛りの列にいる敵の距離を照準器の右上に表示します
- 装甲: 当たった面(正面、側面、背面、上面)の装甲厚を、入射角で厚くなった分も含めて貫通力と比べます。貫通力は距離で下がり、約72度より浅い角度では跳弾します。重戦車の正面は貫通できないので、側面や背面に回り込みます
- 遮蔽物: 家と木は弾を止め、戦車は通り抜けられません。敵は遮るもののない線が通っているときだけプレイヤーを見つけて撃ちます
- 敵: 軽戦車、中戦車、重戦車の3種類です。依頼者の要望で、最初のステージは中戦車との1対1、2つ目から3両(中戦車1、軽戦車2)で、その後は1両ずつ増え、重い戦車が増えます。軽戦車と、最後に残った1両は、近づいて側面へ回り込みます。敵は1発ごとに狙いを詰め、プレイヤーが30m以上動くと狙いがやり直しになります。重戦車は止まっている間、正面をプレイヤーに向けます
- 画面: 地面はkartと同じく行ごとの回転・拡大で描き、戦車は16方向、家は8方向の絵を距離で縮めます。広角では見えている敵の上に赤い印を出します。左下のレーダーは砲塔の向きが上で、見えた敵と被弾の方向を示します

戦車の絵は箱を組み合わせた模型を光線で描いたもので、16方向×車体と砲塔×3種類、家8方向、木2種類、遠くの丘を1枚(640x164)にまとめています。地面(256x256、1ピクセル4m)、この絵、照準器の円形マスクはIKA1形式でフラッシュに置きます。

## train(オリジナルの電車の運転)

`games/train` は新規に書いた電車の運転ゲームです。運転台から見た海沿いの路線を走らせ、6駅(5区間、7.0km)の停止位置目標にぴったり、時刻表どおりに止めます。線路、ホーム、架線、踏切、標識、家や木はすべてコードで描いた独自のもので、既存のゲームの素材や名前は使っていません。Ebitengine のAPIだけで書いているため、本物のEbitengineでもビルドできます。

- 操作: ジョイスティックの上下でワンハンドルのマスコンを1段ずつ動かします(上が力行側、下がブレーキ側。押し続けると0.3秒後から0.1秒ごとに進みます)。段はP5〜P1、N、B1〜B8、EBの15段で、画面右の段表示と下の文字で示します。A(Z、Space)で警笛、B(X)でNに戻します
- 加速とブレーキ: P5は35km/hまで3.0km/h/s、それより上は出力一定で速度に反比例して弱まります。ブレーキは1段0.45km/h/s(B8で3.6km/h/s)、EBは4.5km/h/sです。ブレーキは毎秒4.0km/h/sずつ立ち上がり、緩むので、B8まで約0.9秒かかります。走行抵抗と勾配(1‰あたり0.035km/h/s)も加わります
- 路線: 制限速度は45〜95km/hで、曲線5か所、15‰の上り坂と下り坂、踏切2か所、鉄橋、海岸があります。列車の長さを80mとし、下がる制限は先頭が、上がる制限は最後尾が通り過ぎてから効きます
- 停止: 停止位置目標(黄色の標識)の前後40m以内で止まるとドアが開き、採点します。手前300m、200m、100mに距離標があり、画面下に残りの距離(10m未満は0.1m単位)を表示します。40mを超えて行き過ぎるとオーバーラン、終点では停止位置の35m先の車止めで止まります
- 制限速度: 超えている間は0.5秒ごとに1点減点し、10km/h超えるとATSが非常ブレーキをかけ、止まるまでハンドルが効きません
- 採点(1駅100点): 停止位置は誤差25cm以内で50点、1mごとに8点減。時刻は到着時刻との差が1秒以内で30点、1秒ごとに3点減。乗り心地は20点で、止まる瞬間にB6以上のブレーキがかかっていると10点減、走行中のEB 1回で10点減。ほかに速度超過(ATSとオーバーランは各20点減)、踏切手前の笛標識を過ぎてから120m以内に警笛を鳴らすと5点、鳴らさないと5点減。5駅の平均でS(90以上)、A、B、C、Dのランクを付けます
- 時刻表: 自動運転(制限の3km/h下で走り、約2km/h/sの制動で止まる)の走行時間に3〜5秒の余裕を足し、5秒単位に丸めました。停車は20秒で、遅れて着いたときは到着の20秒後に発車します
- タイトル画面: 自動運転のデモが全線を走り、各駅で3秒止まり、終点の後は最初からやり直します

### 描き方

カメラは線路の上3m、焦点距離は100ピクセル(横約62度)、地平線は上から36行目です。地平線より下の各行が見る地面の距離は `3×100/(行−36)` で決まります(最も手前の行で約6.7m)。前方360mの曲率を5mごとに2回積分して線路の横ずれを求め、各行で地面、道床、枕木、レールを横向きの帯として塗ります。地面は12mごとに濃淡を変え、枕木は1行が0.5m未満を表す手前の行にだけ描きます。

高さのある面も同じ考え方で行ごとに描きます。ホーム(高さ1.1m)の上面は `(3−1.1)×100/(行−36)` の距離に見え、線路側の側面はその距離から地面の距離までの範囲です。上屋(高さ4m)と架線(5.5m)は地平線より上の行に、1行ずつ描きます。架線柱、標識、家、木、上屋の柱は距離で縮めた画像を遠い順に描きます。遠くの山は、線路の曲がった角度の分だけ横にずらします。

### メモリ

描画に使う文字列は固定の配列に組み立て、`Draw` はヒープを確保しません。`NewGame` 以外の確保は、ゲーム開始時の `Game` の初期化(約2.5KB)でした。複合リテラルがヒープに作られていたため、ゼロ値の変数からコピーするように変えました。

画像はすべて初期化でコードで描きます。最初は、TinyGoで起動時に約36KB(366回)のヒープ確保がありました。TinyGoはパッケージの初期化をコンパイル時に実行して結果をプログラムに埋め込みますが、次のものがあると、その部分を実行時に回していました。

- `math.Hypot`、`math.Sin`、文字列の連結: 整数の計算に書き換えました。山の形はBhaskaraの近似式を整数で計算します
- ほかのパッケージ変数(`stations`)から計算した変数: 定数にしました
- 1000回を超えるループ(山の画像160×12ピクセル): 40列ずつ描く関数に分けました

Linux向けのTinyGoで、trainをimportしただけのプログラムの起動時の確保が、importしない場合と同じ2回になることを確認しました。ランチャーでは、trainの画像と変数で静的RAMが約17KB増えます(バッジ向けのリンク結果のシンボルの合計)。
