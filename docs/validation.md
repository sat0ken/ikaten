2026-11-03。実装と検証を同じワークスペースで行いました。実機はTinyGo Conference 2026 badge(ESP32-S3)とGopher Board(RP2040-Zero)で確認しました。ESP32無印は実機が未接続のため未確認です。

- Go 1.27.1、Linux amd64
- TinyGo 0.44.0、LLVM 22.1.4（このマシンのインストール）

- 互換ビルド: Ebitengine v2.10.5、GOOS=js、GOARCH=wasm

## メモリと割り当て

`tinygo build -size short` のbounceサンプルの結果です。RAM欄は **data + bssのみ**で、起動後のヒープや実行時スタックの使用量を含みません。

| ターゲット | code | data | bss | flash合計 | 静的RAM合計 |
| --- | ---: | ---: | ---: | ---: | ---: |
| badge | 63,632 | 3,208 | 21,312 | 66,840 | 24,520 |
| esp32s3 | 60,624 | 3,168 | 21,240 | 63,792 | 24,408 |
| esp32 | 61,576 | 3,216 | 5,368 | 64,792 | 8,584 |
| pico | 56,328 | 3,304 | 6,364 | 59,632 | 9,668 |
| gopher-badge | 56,296 | 3,376 | 6,364 | 59,672 | 9,740 |

フラッシュ画像のサンプル（badge）の文字列埋め込み版はdata=3,200B、bss=21,304B。変更前の可変 `[]byte` 埋め込み版ではdata=3,752B、bss=21,856Bで、ファイル本体相当の静的RAM増加を確認しました。画像は `NewImageFromString` によりコピーせず参照します。

GoのAllocsPerRunで、Clear/Fill/DrawImage（平行移動と回転）/行読み出し、Presentの変更なしフレーム、文字、図形、キー列挙の継続処理が **0 allocs** になることを確認しました。

`tinygo build -print-allocs=.` をbounceとsnakeに実行しました。エンジンとドライバで報告された箇所は、画像、ボタン状態、液晶の初期化、初回または解像度変更時のPresentバッファの確保だけで、Update、Draw、文字描画、変更行処理には報告されませんでした。snakeでは毎フレームの `fmt.Sprintf` と `append` がゲーム側の確保として報告されます(元のソースのままです)。SubImageと動的Layoutの再確保は許容しています。

ホストの16×16不透明スプライト描画ベンチマークは約208ns/op、0B/op、0allocs/opでした（Core i5-1145G7）。**この値は実機の性能予測には使用しません。**

## バッジでの実測

環境はTinyGo Conference 2026 badge(ESP32-S3、240MHz)、既定の `-opt=z` です。生ログは [measurements/2026-11-03-badge.txt](measurements/2026-11-03-badge.txt) にあります。

### SPI全画面転送(240x240、1フレームあたり)

| 要求周波数 | 1行ずつ | 4行ずつ | 計算上の下限 |
| --- | ---: | ---: | ---: |
| 20MHz | 56.4ms | 52.0ms | 46.1ms |
| 40MHz | 32.5ms | 28.6ms | 23.0ms |
| 80MHz | 20.7ms | 17.0ms | 11.5ms |

1行転送と4行転送の差から、転送の窓設定は1回あたり約21µsです。全行変更時に連続行をまとめると、80MHzで約3.7ms短縮できます。

**決定:** バッジのSPI既定値は80MHzにしました。目視で表示の乱れがなく、40MHzより全画面転送が約12ms短いためです。汎用の `esp32s3` ターゲットは配線と液晶が不明なので40MHzのままです。連続行の統合は実装しますが、効果がより大きい `Present` の高速化と合わせて行います。

### スプライト描画(16x16、1枚あたり)

| 画像 | 変更前 | 変更後 |
| --- | ---: | ---: |
| RAM、不透明 | 55.2µs | 56.0µs |
| RAM、マスク付き | 129.2µs | 54.6µs |
| フラッシュ、不透明 | 145.2µs | 46.7µs |
| フラッシュ、マスク付き | 132.8µs | 63.9µs |

変更後はフラッシュとRAMの差が小さく、頻用画像をRAMへコピーする必要はありません。

**判断(タスク3):** マスク付き30枚のシーンは約60msで33.3msに収まらなかったため、高速経路を実装しました。bounceをマスク付きにしたときの `Draw` は8.8msから約6.95msに短縮しました。ただし、FPSはほぼ変わりません。支配的なのは `Present` です。

### benchmark(240x240、スプライト30枚)

| 構成 | FPS | TPS | Draw | Present |
| --- | ---: | ---: | ---: | ---: |
| 40MHz、`-opt=z` | 15〜16 | 46〜48 | 6.4ms | 61.7〜61.9ms |
| 80MHz、`-opt=z`、高速経路の実装前 | 16〜18 | 50〜56 | 6.4ms | 51.0〜51.4ms |
| 80MHz、`-opt=z`、高速経路の実装後 | 16〜18 | 50〜56 | 6.5ms | 51.2〜51.5ms |
| 80MHz、`-opt=z`、マスク付き、実装後 | 16〜18 | 50〜56 | 7.0ms | 51.1〜51.5ms |
| 40MHz、`-opt=2`、実装前 | 16〜17 | 49〜51 | 6.4ms | 53.5〜54.5ms |
| 80MHz、`-opt=2`、実装前 | 19〜21 | 57〜60 | 6.4ms | 43.2〜44.0ms |

この時点では性能目標の30 FPS / 60 TPSは未達でした。1フレームが約58msかかり、1回の描画あたりの `Update` が上限の3回に達するため、TPSも60を下回りました。画面が変わらないフレームでも `Present` は22.9msかかっていました(`-opt=z`、行の読み出しとハッシュの計算)。

### `Present` の高速化

等倍でフレームバッファをコピーせず転送し、連続する変更行を1回の転送にまとめ、ハッシュを16bit単位にして、行の展開を拡大時だけにしました。同じbenchmarkの結果です。

| 構成 | 10秒あたりのフレーム数 | TPS | Draw | Present |
| --- | ---: | ---: | ---: | ---: |
| 80MHz、`-opt=z` | 425〜433 | 60 | 6.5ms | 16.6〜17.0ms |
| 80MHz、`-opt=z`、マスク付き | 419〜427 | 59 | 6.8ms | 16.6〜17.0ms |
| 80MHz、`-opt=2` | 418〜426 | 59〜60 | 6.6ms | 16.9〜17.3ms |
| 40MHz、`-opt=z` | 294〜301 | 60 | 6.5ms | 26.8〜27.5ms |

変更のないフレームの `Present` は22.9msから2.7msになりました。

**性能目標の30 FPS / 60 TPSをバッジで達成しました**(約43 FPS)。

**決定:** `-opt=z` のままにします。`-opt=2` に速度の利点がなくなり、コードだけが約74KBから約124KBに増えるためです。

`Present` はメモリ上のピクセルをそのまま送ります。可変画像の透明ピクセルは常に0で、黒への平坦化と同じ結果になるためです。この前提は `TestRGB565RowsMatchFlattenedRows` で確認しています。ハッシュの衝突で変更を見逃す可能性は、以前と同様に残ります。

高速化の後も、テスト、`make smoketest`(29ビルド)、`make compat`、`tinygo test`、`-print-allocs` の結果は変わらず成功です。`Present` のヒープ確保は初回と解像度変更時だけです。snakeのWASMの開始画面は変更前とピクセル単位で一致しました。

### 30分連続実行

`Present` の高速化後の最終コード、80MHz、bounce(スプライト30枚)で実行しました。

| 項目 | 結果 |
| --- | --- |
| 動作 | 30分後に `Termination` で正常終了。途中の停止なし |
| 描画フレーム数 | ログの179区間の合計で77,193 |
| `HeapAlloc` | 全区間で134,368B(増加なし) |
| FPS / TPS | 40〜51 / 58〜61(平均 約42.7 / 約59.4) |
| `Draw` / `Present` | 約6.5ms / 16.2〜17.0ms |

高速化の前にも同じ30分の実行を行い、停止せず、`HeapAlloc` も同じ値でした(16〜19 FPS)。

ログ末尾の `abort called` は、TinyGoのESP32-S3で `main` が終了したときの通常の出力です(`exit` が `abort` を呼びます)。高速化前のログでは、シリアルの取りこぼしで1行の先頭が欠けています。

### 30分連続実行

bounce(スプライト15枚、120x120を2倍)で、計測値をシリアルではなく画面下に毎秒表示する版を使いました。シリアル出力の停止を避けるためです。2026-11-03 12:54に開始しました。

| 項目 | 結果 |
| --- | --- |
| 動作 | 30分後の `DONE 30min` まで停止なし(依頼者が確認) |
| 終了時の `HeapAlloc` | 228,664B |
| 終了時のGC回数 | 189 |

この版は、表示する文字列を毎フレーム `string([]byte)` で作るため、割り当てが発生します。bounce自体は割り当てがなく、シリアル計測では `HeapAlloc` が42,464Bのまま一定でした。TinyGoの `HeapAlloc` は回収前のごみを含むため(flappyのログでGCの前後に増減しています)、終了時の1回の値からは増加の有無を判断できません。189回のGCを経ても停止しなかったため、ヒープは回収されていると判断しました。

画面のfps=60は、30分経過後にシミュレーションを止め、文字だけが変わる状態での値です。実行中のFPSは上の表の値(約31.7)です。

## dungeon(オリジナルの一人称シューティング)

`games/dungeon` は、レイキャスティング方式の一人称シューティングを新規に書いたものです。マップ、敵(スライム)、武器、壁の模様はすべてコードで生成した独自のもので、既存のゲームの素材は使っていません。Ebitengine のAPIだけで書いているため、`make compat` でimportパスを書き換えるだけで本物のEbitengineでもビルドできます。

描画は、壁の縦1列ずつを1ピクセル幅の `SubImage` として拡大して描きます(120列)。距離による暗さは `ColorScale`、敵は奥から順に描き、壁より奥の列は飛ばします。

| 確認 | 結果 |
| --- | --- |
| WASM(ヘッドレスChromium、自動操作) | 壁、床、天井、武器、照準、マズルフラッシュ、HUDの描画を確認 |
| ホストのテスト(作業ツリー外のコピー) | スライムの表示と遠近、命中、被弾時の点滅、壁の向こうの敵に当たらないことを確認 |
| `make smoketest` | 8サンプル×6ボードと7サンプル×WASMの55ビルドすべて成功 |
| `make compat` | 成功 |

### Gopher Boardでの実測

120x120を2倍表示し、自動操作の計測版で測りました。シリアル出力が止まる問題(「RP2040のシリアル出力」参照)のため、10秒ごとの値を画面上部に表示し、依頼者が撮った写真から読み取りました。区間ごとの時間は、作業ツリー外のコピーで `Draw` に計測を加えた版のものです。

| 版 | 10秒あたりのフレーム数 | `Draw` | `Present` | 主な変更 |
| --- | ---: | ---: | ---: | --- |
| 最初 | 35 | 271.6ms | 20.1ms | — |
| 1 | 117 | 63.1ms | 22.0ms | 汎用経路の行の開始位置を固定小数点で足す |
| 2 | 161 | 41.1ms | 20.4ms | 回転のない拡大縮小を専用の経路にし、準備をfloat32にする。不透明な整数倍拡大を区間で書く |
| 3 | 205 | 28.7ms | 19.5ms | 同じソース行を使う行をまとめ、色を1回だけ計算して縦に書く。NaN判定と単位の `ColorScale` を浮動小数点なしにする |
| 4(最終) | 212 | 27.8ms | 18.9ms | `ColorScale` の変換をビット演算にする。区間の書き込みを直接行う |

最終版は約21 FPS、59〜60 TPSです。最終版の1フレームの内訳は、壁23.4ms(うち光線の計算5.2ms)、天井と床1.2ms、スライム0.3ms、武器とHUD0.8msです。計測値の文字表示に約0.9msかかっていますが、通常版にはありません。

RP2040(Cortex-M0+)には浮動小数点演算器がありません。最初の版では、1ピクセル幅の列を描くたびに汎用経路が行ごとにfloat64を計算しており、これが大部分でした。ソフトウェアのfloat32は1演算あたり約100サイクルと見積もられ(光線の計算から逆算)、最終版でも壁1列の `DrawImage` に約150µsかかります。その約3分の2は呼び出しごとの準備です。`Present` は画面全体が毎フレーム変わるため、2倍表示の転送に約19msかかります。30 FPSには `Draw` を約13msにする必要があり、DMA転送や第2コアの検討対象です。

## all(全ゲームのランチャー)

`games/all` は、これまでのゲーム8本をメニューから選んで遊べるランチャーです。上下で選んでA(Z)で開始し、ゲーム中にAとB(ZとX)を1秒押し続けるとメニューに戻ります。押している間は画面上端にバーが伸びます。各ゲームのLayout(120x120または240x240)はそのまま使い、エンジンが画面を確保し直します。Ebitengine のAPIだけで書いているため、`make compat` で本物のEbitengineでもビルドできます。

`TestEveryGameStartsAndReturns` は、`RunGame` を通して8本を順にメニューから開き、少し遊んでからAとBを押し続けてメニューへ戻ることを確認します。blocksは最初の `Update` で場面を作るため、ゲームを選んだ直後に `Draw` が先に呼ばれるとpanicしました。Ebitengineと同じく、ランチャーはゲームが一度 `Update` するまで描画しないようにしました。

### バッジでのメモリ

作業ツリー外のコピーで、各ゲームを10秒ずつ順に開き、`runtime.GC` の後の `HeapAlloc` を表示しました。生ログは [measurements/2026-11-04-badge.txt](measurements/2026-11-04-badge.txt) の末尾にあります。

| 版 | 結果 |
| --- | --- |
| 最初 | flappy(240x240)からメニューに戻ると222KBに増え、blocks(240x240)を開いたところでメモリ不足で停止 |
| 画面のメモリを使い回す | 2周して停止なし。uboatで最大約307KB |
| uboatの大きな画像をフラッシュへ | 2周して停止なし。最大約203KB、flappyの後は194〜203KBで一定 |

1つ目は、Layoutが変わるたびに画面を新しく確保していたためです。古い画面はPCのGoでは回収されましたが、TinyGoの保守的なGCではスタックに残った古い値から参照されたままになりました。そこで `RunGame` の画面の確保し直しを、今の画面のメモリに収まる場合は使い回すように変えました(`resizeScreen`、`TestResizeScreenReusesMemory`)。画面のメモリは遊んだ中で最大のゲームの分(240x240で約122KB)を保持します。

- 車体と砲塔: 砲塔は車体と別に回り、車体が旋回しても砲塔は同じ方位を向き続けます(スタビライザー)
- 弾の落下: 弾は1ティックに10m進み、重力で落ちます。照準器の中心の下に200mごとの距離目盛り(2、4、6、8、10)があり、目標の距離の目盛りの間に目標を置くと当たります。目盛りの列にいる敵の距離を照準器の右上に表示します

- 遮蔽物: 家と木は弾を止め、戦車は通り抜けられません。敵は遮るもののない線が通っているときだけプレイヤーを見つけて撃ちます

戦車の絵は箱を組み合わせた模型を光線で描いたもので、16方向×車体と砲塔×3種類、家8方向、木2種類、遠くの丘を1枚(640x164)にまとめています。地面(256x256、1ピクセル4m)、この絵、照準器の円形マスクはIKA1形式でフラッシュに置きます。

## train(オリジナルの電車の運転)

`games/train` は新規に書いた電車の運転ゲームです。運転台から見た海沿いの路線を走らせ、6駅(5区間、7.0km)の停止位置目標にぴったり、時刻表どおりに止めます。線路、ホーム、架線、踏切、標識、家や木はすべてコードで描いた独自のもので、既存のゲームの素材や名前は使っていません。Ebitengine のAPIだけで書いているため、本物のEbitengineでもビルドできます。

- 操作: ジョイスティックの上下でワンハンドルのマスコンを1段ずつ動かします(上が力行側、下がブレーキ側。押し続けると0.3秒後から0.1秒ごとに進みます)。段はP5〜P1、N、B1〜B8、EBの15段で、画面右の段表示と下の文字で示します。A(Z、Space)で警笛、B(X)でNに戻します
- 加速とブレーキ: P5は35km/hまで3.0km/h/s、それより上は出力一定で速度に反比例して弱まります。ブレーキは1段0.45km/h/s(B8で3.6km/h/s)、EBは4.5km/h/sです。ブレーキは毎秒4.0km/h/sずつ立ち上がり、緩むので、B8まで約0.9秒かかります。走行抵抗と勾配(1‰あたり0.035km/h/s)も加わります
- 路線: 制限速度は45〜95km/hで、曲線5か所、15‰の上り坂と下り坂、踏切2か所、鉄橋、海岸があります。列車の長さを80mとし、下がる制限は先頭が、上がる制限は最後尾が通り過ぎてから効きます
- 停止: 停止位置目標(黄色の標識)の前後40m以内で止まるとドアが開き、採点します。手前300m、200m、100mに距離標があり、画面下に残りの距離(10m未満は0.1m単位)を表示します。40mを超えて行き過ぎるとオーバーラン、終点では停止位置の35m先の車止めで止まります
- 制限速度: 超えている間は0.5秒ごとに1点減点し、10km/h超えるとATSが非常ブレーキをかけ、止まるまでハンドルが効きません
- 採点(1駅100点): 停止位置は誤差25cm以内で50点、1mごとに8点減。時刻は到着時刻との差が1秒以内で30点、1秒ごとに3点減。乗り心地は20点で、止まる瞬間にB6以上のブレーキがかかっていると10点減、走行中のEB 1回で10点減。ほかに速度超過(ATSとオーバーランは各20点減)、踏切手前の笛標識を過ぎてから120m以内に警笛を鳴らすと5点、鳴らさないと5点減。5駅の平均でS(90以上)、A、B、C、Dのランクを付けます
- 時刻表: 自動運転(制限の3km/h下で走り、約2km/h/sの制動で止まる)の走行時間に3〜5秒の余裕を足し、5秒単位に丸めました。停車は20秒で、遅れて着いたときは到着の20秒後に発車します
- タイトル画面: 自動運転のデモが全線を走り、各駅で3秒止まり、終点の後は最初からやり直します

### 描き方

カメラは線路の上3m、焦点距離は100ピクセル(横約62度)、地平線は上から36行目です。地平線より下の各行が見る地面の距離は `3×100/(行−36)` で決まります(最も手前の行で約6.7m)。前方360mの曲率を5mごとに2回積分して線路の横ずれを求め、各行で地面、道床、枕木、レールを横向きの帯として塗ります。地面は12mごとに濃淡を変え、枕木は1行が0.5m未満を表す手前の行にだけ描きます。

高さのある面も同じ考え方で行ごとに描きます。ホーム(高さ1.1m)の上面は `(3−1.1)×100/(行−36)` の距離に見え、線路側の側面はその距離から地面の距離までの範囲です。上屋(高さ4m)と架線(5.5m)は地平線より上の行に、1行ずつ描きます。架線柱、標識、家、木、上屋の柱は距離で縮めた画像を遠い順に描きます。遠くの山は、線路の曲がった角度の分だけ横にずらします。

### メモリ

描画に使う文字列は固定の配列に組み立て、`Draw` はヒープを確保しません。`NewGame` 以外の確保は、ゲーム開始時の `Game` の初期化(約2.5KB)でした。複合リテラルがヒープに作られていたため、ゼロ値の変数からコピーするように変えました。

画像はすべて初期化でコードで描きます。最初は、TinyGoで起動時に約36KB(366回)のヒープ確保がありました。TinyGoはパッケージの初期化をコンパイル時に実行して結果をプログラムに埋め込みますが、次のものがあると、その部分を実行時に回していました。

- `math.Hypot`、`math.Sin`、文字列の連結: 整数の計算に書き換えました。山の形はBhaskaraの近似式を整数で計算します
- ほかのパッケージ変数(`stations`)から計算した変数: 定数にしました
- 1000回を超えるループ(山の画像160×12ピクセル): 40列ずつ描く関数に分けました

## air(オリジナルの空戦)

`games/air` は新規に書いた空戦ゲームです。操縦席から見た3Dで、選択画面で次の3つから選びます。艦船、飛行機、雲、爆煙、計器はすべてコードで描いた独自のもので、既存のゲームの素材や名前は使っていません。敵の機体と艦は特定の型を描いていません。Ebitengine のAPIだけで書いているため、本物のEbitengineでもビルドできます。

- 零戦(FIGHTER): 味方の空母と駆逐艦2隻の上空で、11km先から高度3000mで来る3波の空襲(爆撃機2・戦闘機1、3・1、4・2)を迎え撃ちます。爆撃機が空母の上空500mに達すると45%の確率で空母に命中し、3発で空母は沈みます。波の間に着艦して弾を補給し、修理されます。A(Z)で7.7mm機銃、B(X)で20mm機関砲です
- 九九式艦上爆撃機(DIVE BOMB): 8km先の敵艦隊(空母、巡洋艦、駆逐艦2隻、12m/sでジグザグ航行)へ高度3000mで向かい、急降下して爆弾を落とします。A(Z)で投下、B(X)でダイブブレーキです。ブレーキを出さないと急降下で制限速度(450km/h)を超え、機体が傷みます。照準器には爆弾の落下を計算した着弾点が出ます。投下後に引き起こしが遅れると海面に突っ込みます
- 九七式艦上攻撃機(TORPEDO): 高度800mで向かい、海面すれすれまで降りて魚雷を落とします。A(Z)で投下、B(X)でスロットルを全開と絞りで切り替えます。高度60m以下、300km/h以下、水平でないと魚雷は折れます。魚雷は35m/s(実物の42ノットより速く、1回の攻撃が1分にならないようにした)で走り、150m走ってから爆発できます。目標艦の未来位置(魚雷と艦の会合点)を黄色の印で示します。艦は魚雷が600m以内に来ると、艦首か艦尾を向けてかわそうとします

### 操縦と飛行

- ジョイスティックの左右でロール、上下でピッチです。操縦桿と同じく、上で機首下げ、下で機首上げです。選択画面のB(X)で上下を逆にできます
- 機体は前と上の向きの2つのベクトルで姿勢を持ちます。操縦桿の引きで荷重倍数(零戦は最大7G、押すと-1G)を決め、揚力と重力の合力で飛行経路を曲げます。そのため、バンクしたまま操縦桿を離すと高度が下がりながら旋回し、引くと鋭く曲がります。宙返りや背面飛行もできます
- 速度は、速度で弱まるプロペラの推力、速度の2乗の抗力、荷重で増える誘導抗力、上昇と降下の重力で変わります。失速速度に近いと揚力が足りず、機首が下がります
- 敵の操縦は、目標を1秒弱で機首に入れるのに必要な揚力の向きにロールして引く、という人間と同じ操作で、同じ飛行モデルで飛びます。敵戦闘機は弾の飛ぶ時間分だけ未来を狙い、照準点の動きも先読みします。後ろに付かれると旋回で振り切ろうとします。爆撃機と九九艦爆・九七艦攻には後部銃座があります
- 敵艦の対空砲火: 高角砲は、6km以内にいる飛行機の未来位置に誤差付きで砲弾を送り、25m以内で炸裂すると損傷します。機銃は2.2km以内で曳光弾を撃ちます

### 描き方

カメラは操縦席の目で、焦点距離は100ピクセル(横約62度)です。画面の点 (px, py) から見る向きの上昇量は `px*r.z - py*u.z + 100*f.z`(r、u、fは機体の右、上、前の単位ベクトル)で、画面上で線形です。そのため、水平線と、海面までの距離が等しい線は、画面上ですべて平行な直線になります。空と海を、この直線で区切った帯として描きます。各帯は1×1の画像を回転した長方形として描くので、三角形のAPIは要りません。海の帯の境目は、高度から距離3万、1万2千、5千、2千、700mになる角度に置くので、高度によって海の見え方が変わります。

艦船と飛行機は、上から見た絵と横から見た絵の2枚を、その場所での透視投影の1次近似(アフィン変換)で描きます。艦は、舷側、甲板、上部構造の順に重ねます。航跡は海面に貼ります。視線から大きく外れた物体はこの近似が合わないので、描きません(最初は画面外の真下の空母の航跡が画面いっぱいに伸びていました)。雲と煙は距離で縮めた絵です。高度500m以下では、海面に白波の点を撒いて速さが分かるようにしています。

敵機は遠いと1ピクセルになるため、4km以内の敵機に赤い角括弧を付け、狙っている敵機や目標艦が画面外にあるときは画面の端に向きを示す印を出します。零戦では、狙っている敵機の未来位置(弾の飛ぶ時間と落下を含む)に黄色の十字を出します。

## fish(オリジナルの船釣り)

`games/fish` は新規に書いた船釣りのゲームです。船から沖へ仕掛けを投げ、海の断面を横から見ながら魚のいる棚(深さ)に合わせ、アタリで合わせて、糸の張りを見ながら取り込みます。朝6時から夕方6時までの1日(約6分)で、釣った魚の重さと種類で点数を競います。魚、船、釣り人、海底の岩と海藻はすべてコードで描いた独自のもので、既存のゲームの素材や名前は使っていません。Ebitengine のAPIだけで書いているため、本物のEbitengineでもビルドできます。

- 投げる: Aを押している間、力のゲージが上下に振れます。離したときの力で、6〜58m先に落ちます
- 沈める: 仕掛けは着水すると海底まで沈みます。Aか上で止め、下で糸を出してさらに沈め、上で巻き上げます。Bで一気に巻き上げて投げ直します。画面は仕掛けを追って上下にスクロールし、右端に10mごとの深さの目盛りがあります
- 誘う: 止めた仕掛けをAでしゃくると、0.8m跳ね上がってゆっくり戻り、1.5秒の間、魚が遠くから寄ってきます(イカは特によく寄る)
- アタリ: 寄ってきた魚は、まず何回か突つき(竿先が小さく揺れる)、そのあと食い込みます(竿先が大きく曲がり、「!」が出る)。食い込みの間にAで合わせると掛かります。突つきのうちに合わせると逃げ(TOO EARLY)、食い込みを見逃すと仕掛けを離します(MISSED)
- やり取り: Aを押している間リールを巻きます。魚は走る時間と休む時間を繰り返し、走っている間に巻くと糸の張り(画面下のゲージ)が上がります。限界を超えて0.25秒続くと糸が切れ、張りのない状態が1.5秒続くと針が外れます。150mの糸を出し切っても切れます。魚は張りと走りで疲れ、疲れるほど走りが短く、休みが長くなります。糸が3.5mまで縮むと取り込めます
- 魚: アジ(3〜15m)、サバ(5〜20m)、マダイ(22〜50m)、ヒラメ(海底近く)、イカ(8〜28m)、タチウオ(12〜35m)、ブリ(10〜40m、まれ)の7種類で、それぞれ大きさ、引きの強さ、走り方、突つく回数、食い込みの長さが違います。朝(8時まで)と夕方(15時半から)はよく食い、タチウオとイカは夕方に増えます。大きい個体ほどまれです。海底に長く置いておくと、まれに古い長靴が掛かります(0点)
- 点数: 重さ(長さの3乗に種類ごとの係数を掛けた値)を100倍した値に、種類ごとのボーナスを足します。結果画面に、種類ごとの数と最大の長さ、合計の重さと点数を出します

空の色は5時半、7時、12時、16時、18時半の色の間を補間し、海は深さ5mごとに暗くなります。太陽は時刻に合わせて空を横切ります。

## bomb(オリジナルの爆弾迷路の対戦)

`games/bomb` は新規に書いた爆弾迷路の対戦ゲームです。主人公はGo Gopherで、4匹のGopherが壁に囲まれた迷路で爆弾を置き合い、最後まで残った1匹がラウンドの勝ちです。2本先取で試合に勝つと次のレベルに進み、CPUのGopherが強くなります。Gopherは参考画像のベージュのGopherをもとに18×22ピクセルのドット絵としてコードで描き(正面、背中、横向きに、立ちと2歩の絵)、CPUの3匹は青、ピンク、緑の色違いです。Go GopherのデザインはRenée French氏によるもので(CC BY 4.0)、NOTICEとタイトル画面にクレジットを書いています。壁、ブロック、爆弾、炎、アイテムもコードで描いた独自のもので、既存のゲームの素材や名前は使っていません。Ebitengine のAPIだけで書いているため、本物のEbitengineでもビルドできます。

- 盤面: 13×11マス(画面は240×240、1マス18ピクセル)。外周と1マスおきの柱は壊れない壁で、残りの72%ほどに壊せるブロックを置きます。4隅のスタート地点の周りは空けます
- 操作: 十字キーで移動、A(Z)で爆弾を置く、B(X)で目の前の爆弾を蹴る。移動は1マスの48分の1単位で、通路から少しずれていても曲がり角に滑り込めるよう、進む先が空いていれば列の中央へ寄せます
- 爆弾: 2.5秒で爆発し、十字に火が伸びます。火は壁で止まり、最初のブロックを壊して止まります。火の届いた爆弾は連鎖して爆発し、火の中のGopherは倒れます。蹴った爆弾は何かに当たるまで滑ります
- アイテム: 壊したブロックの約36%から、火力(+1、最大8)、爆弾の数(+1、最大8)、速さ(+1、最大6)が出ます。火に焼かれると消えます
- 時間: 1ラウンド2分です。残り30秒で「HURRY!」と出て、外周から渦巻き状に壁が落ちてきて、下にいるGopherはつぶれます。最後は全マスが埋まるので、必ず決着がつきます

### CPUのGopher

毎ティック、各マスに火が来るまでのティック数(危険地図)を、爆弾の連鎖とこれから落ちる壁も含めて計算します。CPUは移動をマスの中央でだけ決めます。

1. 自分のマスが危険なら、通る間に火が来ないマスだけをたどる幅優先探索で、火の来ない一番近いマスへ逃げます
2. 相手が射程に入っているか、ブロックを壊せる場所なら、爆弾を置いた場合の危険地図を作り、余裕を持って逃げ切れるときだけ置きます
3. それ以外は、近くのアイテム、相手を狙える場所、ブロックを壊せる場所の順に探して向かいます。ブロックがなくなれば相手を追います

レベルが上がると、相手を狙う割合が30%から85%に上がり、気まぐれに歩く割合が20%から3%に下がります。探索は固定の配列だけで行い、関数値やスライスを作らないので確保をしません。

最初は自分の爆弾で倒れる割合が多すぎました。マスの中央へ歩く途中で、他のGopherが行く手に爆弾を置くと、中央に着くまで考え直さないため、その場で止まって火に巻かれていました。行く手がふさがれたら引き返すように直しました。その後も残る「倒れたCPU」は、逃げ道を相手の爆弾でふさがれたもので、このジャンルの駆け引きとしてそのままにしています。また、ブロックがなくなると中央で待つだけになり、時間切れの引き分けが30戦中7〜9回あったため、相手を追うようにし、残り30秒で壁が迫るようにしました。

## jump(オリジナルの横スクロールアクション)

`games/jump` は新規に書いた横スクロールアクションです。主人公はbombと同じベージュのGo Gopherで、草原(MEADOW)、洞窟(CAVE)、空(SKY)の3ステージを走り、跳び、ダッシュで進み、宝石を集め、ゴールの「PASS」の旗を目指します。敵はプログラマーにちなんだ「バグ」(歩く虫)、波打って飛ぶ蛾、背中にトゲのある虫です。Gopherの絵はGo Gopher(Renée French氏のデザイン、CC BY 4.0)をもとにコードで描いたドット絵で、NOTICEとタイトル画面にクレジットを書いています。地形、敵、宝石、旗、背景もコードで描いた独自のもので、既存のゲームの素材や名前は使っていません。Ebitengine のAPIだけで書いているため、本物のEbitengineでもビルドできます。

- 操作: 左右で走り、A(Z、上)でジャンプ、B(X)でダッシュです。ジャンプはボタンを離すと上昇が弱まるので、押す長さで高さを変えられます(最大約4.3マス、軽く押すと約1.2マス)。足場を離れて6ティックの間と、着地の6ティック前に押したジャンプも有効です
- ダッシュ: 12ティックの間、横に1ティック3ピクセルで進み、重力を受けません。空中では着地まで1回だけ使えます。土のブロックを壊し、当たった敵を倒します
- 敵: 上から踏むと倒せて跳ね返ります。横から当たるとハートが1つ減り、少しの間点滅して無敵になります。トゲの虫は踏むとこちらが傷つくので、ダッシュで倒します

- 地図: 1ステージは180〜190×15マス(1マス8ピクセル)の文字列です。画面は240×240で、ゲームの座標を2倍にして1マス16ピクセルで描きます。草原の途中には跳び越せない高さの土の壁を置き、ダッシュの使い方を覚えさせます

## 240×240の試験(試験用ブランチ `claude/hires-240-test`)

この節は試験の記録です。結果を受けて240×240を正式に採用し、ビルドタグ `ikaten_hires` は廃止しました(次の節)。

これまでのゲームは120×120を2倍に拡大して表示しています。240×240で作った場合にFPSがどれだけ下がるかを確かめるため、jump(画面全体がスクロールする重い例)とbomb(盤面がほとんど止まっている例)を、ビルドタグ `ikaten_hires` で240×240にできるようにしました。ゲームの座標と処理は120×120のままで、描画だけを2倍の解像度で行います(`put` が全ての描画に2倍の拡大を掛け、`Layout` が240×240を返します)。絵は2倍に拡大して描くだけですが、塗るピクセル数は本物の240×240版と同じなので、性能の比較には足ります。ただし、デバッグ用フォントの文字は大きさが変わらないので小さく見えます。

jumpのタイトル画面では、Gopherが自動で草原を走るようにしました(壁、穴、トゲ、虫の前で跳び、土の壁と落ちかけた穴でダッシュ)。バッジではジョイスティックの読み取りが毎ティック矢印キーを上書きするため、ベンチマークから走らせることができないからです。jumpのベンチマークはキーを押さずにタイトルのまま測ります。

### 変わった部分だけ描き直す

ikatenに、Ebitengineと同じ `SetScreenClearedEveryFrame` と `IsScreenClearedEveryFrame` を加えました。既定はこれまでどおり毎フレーム画面を消します。消さない設定では前のフレームの画面がそのまま残りますが、`Layout` で大きさが変わったときは、使い回すメモリに別の大きさの画素が残っているので1回だけ消します(`TestScreenClearedEveryFrame`)。

bombはこれを使い、変わったマスだけ描き直すようにしました。

- マスごとに、描き方を決めるもの(壁・ブロック・床、上の影、アイテム、崩れかけ、炎の向きと太さ)を1つの数にまとめ、前のフレームと違うマスだけ描き直します
- Gopherと爆弾は、今のフレームと前のフレームで重なるマスを描き直したうえで、毎フレーム上に描きます
- 上下の表示は、時計の秒、勝ち数、能力、レベルが変わったときだけ描き直します
- 新しい画面、毎フレーム消される設定(テストやEbitengineで消す設定にした場合)、盤面に重なる箱(READY、HURRY!、勝敗)が出入りしたときは、全部描き直します
- ランチャーは、ゲームを始める前とメニューに戻るときに、毎フレーム消す設定に戻します

`TestDrawOnlyChanges` は、試合を12000ティック進め(爆風、倒れるGopher、迫る壁、ラウンドの間の箱、試合の終わりを含む)、7ティックごとに、描き直しを減らした画面と全部を新しく描いた画面が1画素も違わないことを、120×120と240×240の両方で確かめます(1715フレーム)。Gopherの重なるマスの描き直しを外すと、91ティック目で違いを見つけて失敗することも確かめました。本物のEbitengine v2.10.5でもビルドし、Chromiumで動かして、動いたGopherの跡が残らないことを確認しました。

### 240×240についてのまとめ

- バッジ(ESP32-S3)では240×240で作れます。転送の時間は120×120の2倍表示とほとんど変わらず、増えるのは描画です
- 盤面の多くが止まっているゲームは、`SetScreenClearedEveryFrame(false)` で変わった部分だけ描き直せば60 FPSを出せます(bomb)
- 画面全体がスクロールするゲームは、全部を描き直しても約50 FPS、重い区間で37 FPSでした(jump)
- 画面の約122KBが要るので、ESP32無印のボードには収まりません。行ごとに計算する疑似3D(air、train、kart)の240×240は測っていません

## 240×240への移行

試験の結果を受けて、オリジナルのゲーム(train、air、fish、bomb、jump、dungeon、shooter、kart、uboat、tank)を240×240専用にし、絵を細かく描き直します。120×120版は残しません。数回に分けて進め、この節に順に追記します。

- 対象はバッジ(ESP32-S3)です。画面だけで約122KBを使うため、ESP32無印には対応しません。`scripts/smoketest.sh` は240×240専用の例をESP32無印向けにビルドしません
- RP2040(Gopher Board、Pico、Gopher Badge、RAM 264KB)向けのビルドは通りますが、実機では確かめていません。ランチャーは静的RAMだけで約106KBあり、画面と合わせると入らない見込みです
- 移植した例(snake、flappy、blocks)と bounce はそのままです

### 共通の変更

- `games/pixtext`: 240×240のゲームで共有する5×7ピクセルのフォントです。行を固定のバッファに組み立てるので、得点を描いても確保をしません。色ごとに全グリフを描いた画像を8色分持ち回し、白のグリフに色を掛けて1画素ずつ計算する遅い経路を避けます。透明度のある色だけ色を掛けて描きます。Ebitengineでは `scripts/compat.sh` がこのパッケージも一緒にビルドします
- ikatenの描画の内側のループを、バッジで実測しながら書き直しました(下の「バッジでの描画の速さ」)
- 透明な画素のないタイルは、作るときに先に `Fill` して不透明な画像にします。不透明な画像はマスクを見ずに行ごとコピーされます
- ランチャーのメニューも240×240にし、pixtextで描きます。bounceはランチャーからも30枚で動きます

### bomb と jump(第1弾)

どちらもゲームの規則と座標はそのままで、描画を240×240で書き直しました。テストは変えずに通ります。

- bomb: 1マス18ピクセル。Gopherは18×22で、輪郭、陰、明るい部分、白目と瞳、鼻と歯、手足を描き、正面・背中・横向きに立ちと2歩の絵があります(歩くと「歩・立・歩・立」)。壁は面取りした石、ブロックはレンガ、草は2種類の模様、爆弾は光沢と導火線の火花です。炎は中心、腕、先端の7種類の絵を、揺らめき2つと消えかけの3段階で用意しました(端が波打ち、外から赤、橙、黄、白)。変わった部分だけ描き直す仕組みはそのままで、`TestDrawOnlyChanges` は240×240で1715フレームを比べます
- jump: ゲームの1ピクセルを画面の2ピクセルとし、位置は小数から画面の座標へ直すので、動きは前より細かくなります。Gopherは18×22(立ち、2歩、両手を上げたジャンプ、前のめりのダッシュと速度線)、敵は16×12、宝石は12×12で光ります。地面は草の縁と土の粒、開いた側の縁取り、ブロックと土の壁はステージごとの色で描きます。遠くの雲がゆっくり流れます。空が画面全体を覆うので画面を消す設定を切り、最初に1回だけ画面全体を `Fill` して不透明にします
- 両方とも、`Draw` がホストで確保しないことをテストします。TinyGoの `-print-allocs` でも、割り当ては `NewGame` だけです(jumpの山の作業用配列は、マイコンではスタックに置けずヒープへ行くため、パッケージの変数にしました)

### バッジでの描画の速さ

最初の版をバッジで測ると、bombは60 FPSを保ちましたが、jumpは試験の版より遅くなりました。

bombのヒープは試験の版の140KBから256KBに増えました。Gopherと炎の絵が4倍の画素になり、フォントの色ごとの画像も持つためです。

ホストでは試験の版より速かったため、最初は描画の呼び出しの回数を疑いました(394回、試験の版は237回。山の帯の塗りが249〜364回)。山を画像に描いておく形にし、地面の連なりを縦長の画像1枚で描くようにして、139回に減らしました。その際、地面の連なりを飛ばすはずの行のループが、Go 1.22以降の `range` ではループ変数を書き換えても飛ばないため、地面を3回重ねて描いていたことにも気づいて直しました。ところが、バッジでの `Draw` は16〜28msと変わりませんでした。

そこで、描画の種類ごとの時間を測る `examples/drawprobe` を作りました(RAM上の画像だけで測り、液晶には送りません)。jumpの `Draw` も、ベンチマークのビルドでは背景、タイル、敵、Gopher、表示、箱の区間ごとの時間を出すようにしました。わかったのは次のことです。

- 呼び出し1回の準備は約5µsで、重くありません。重いのは画素あたりの時間で、塗りは約80〜100ns、16画素の行のコピーは1行約3µsでした
- 1行(240画素)を書く方法を比べると、組み込みの `copy` は24µs、16ビットずつのループは8µs、32ビットずつのループは4µs、それを4回展開すると3µsでした。`copy` はESP32-S3のROMの `memmove` を呼び、これが遅いのです。ホスト向けに入れた「上の行をコピーして塗る」高速化は、バッジではかえって遅くしていました
- TinyGoが出力したLLVM IRを読むと、`Image.Fill` などは1画素ごとにバッファへのポインタ、nilの確認、スライスの長さを読み直していました。書き込みがそれらを変えるかもしれない、とコンパイラーが判断するためです

ikatenを次のように直しました。

- 塗りとコピーの内側のループは、スライスをローカル変数に置き、行の境界がそろっていれば2画素ずつ32ビットで書きます(`internal/raster/pixels.go`)。LLVM IRで `memmove` を呼ばないことを確かめています
- マスク付きの行、整数倍の拡大、縮小、変形、`Fill` も、スライスをローカル変数に置きます。マスク付きの行は、マスクを1バイト(8画素)ずつ読み、全部透明なら飛ばし、全部見えるならまとめてコピーします
- 左右を反転した絵(`Scale(-1, 1)` と整数の位置、色の変更なし)に専用の経路を加えました。これまでは一般の変形の経路を通っていました
- 全体が不透明な描画先(`Fill` した画面など)には、マスクを書き直しません。描画先が不透明ならマスクは全部立っているという、他の経路と同じ前提です
- それぞれ、汎用の経路と同じ画素になることを、全部のアラインメント、不透明とマスク付き、RAMとフラッシュの画像、描画先の不透明とそうでない場合でテストします

jumpも、山を各ステージの高さで画像に描いておき(洞窟の天井も別の画像)、すべて等倍で描くようにし、山の裾より下の空は塗らないようにしました。

### ランチャーのRAM

第2弾を作る途中で、ランチャー(all)のバッジ向けビルドの静的RAMが約324KBになっていることに気づきました。第1弾の前は約234KBです。ESP32-S3でプログラムが使えるDRAMは約398KB(`esp32s3.ld` のヒープの終わりまで)で、240×240の画面に約122KBが要るため、このままでは入りません。各ゲームが絵をパッケージの初期化で作っていたため、ランチャーは全部のゲームの絵を同時に持ち続けていました。TinyGoはその多くをコンパイル時に作り、静的RAM(bss)に置きます。

そこで、bomb、jump、fish、trainの絵(jumpの山と地面の画像も)を、パッケージの変数ではなく `NewGame` で作り、Gameが持つようにしました。ランチャーではメニューに戻るとゲームごと捨てられ、GCで回収されます。単体で動かすときの合計は変わりません(静的RAMからヒープに移るだけです)。

| ランチャー(all) | 第1弾の前 | 第2弾の途中 | 絵をGameが持つようにした後 |
| --- | ---: | ---: | ---: |
| バッジ向けビルドの静的RAM | 約234KB | 約324KB | 約189KB |
| 初期化の後に残るヒープ(ホストのGo、テストの分を含む) | 約396KB | 約554KB | 約400KB |

`go test ./games/all` は、各ゲームを開いてメニューに戻ったときのヒープが同じであることを確かめています。以後のゲームも、大きな画像はGameに持たせます。

### tank(第4弾)

規則はそのままで、描画を240×240で書き直しました。焦点距離は広角208、拡大1664ピクセル/ラジアン(8倍)、照準の中心は(120,108)、拡大時の円は半径102ピクセルです。仰角を上げ下げする速さは角度で前と同じにしています。

- 戦車、家、木の絵を1mあたり8ピクセル(前は4)で光線で描き直しました。戦車は80×36の枠に、転輪、履帯の上のフェンダー、後ろの排気管、車体の機銃、砲口の制退器、砲塔の後ろの物入れ、アンテナを加えました。家は104×72、木は40×80で、葉の塊ごとに陰を付けました。シートは1280×296で約805KB、フラッシュに置きます
- 地面の画像を1ピクセル2m(前は4m)の512×512にし、畑の境目に暗い線を加えました。約512KBで、フラッシュに置きます。地面はkartと同じく、1行を行の画像に描いてから縦2倍で画面へコピーします
- 遠くの丘は空の色を下に塗った不透明な512×32の帯にし、その上の空だけを塗ります(uboatで、マスク付きの広い画像が遅いとわかったため)
- 拡大時の照準の枠は、uboatの潜望鏡と同じく、行の帯ごとの暗い長方形と、曲線と縁だけの小さな画像(RAM)で描きます。照準の画像(フラッシュ)はなくしました
- 照準の目盛、距離の数字、レーダー(62ピクセル)、計器、タイトル、結果の文字をpixtextで描き直しました
- 絵はGameが持ちます。画面は一度塗って不透明にし、クリアしません。`Draw` が確保しないことのテストを加え、ベンチマークのビルドでは区間ごとの時間(空と丘、地面、戦車などの物、照準と計器)を出します
